Replay of Run #3 from Brindle Coffee: 16 deliveries in 43.2 s, shown faster.

Delivery 1 of invoice.paid: 200, orders.count 1. Delivery 2, same event: 200, orders.count 2. Finding: Duplicate delivery created a second order.

Every response said 200. Three things were wrong.

Run #3 sent 16 deliveries to Maya's Express handler. Status codes alone would have passed it. The probe and the signatures did not.

Critical

Accepts tampered payload

D12 amount_paid 2400 → 0
HTTP 200 in 167 ms · orders.count 0 → 1
expected: a 4xx and no change

If a failed check doesn't stop the request, anyone who can reach this URL can create paid orders.

FixReturn 400 as soon as constructEvent throws, before any write.
Stripe docs › Webhooks › Verify signatures
High

Duplicate delivery created a second order

D5 same event as D4
HTTP 200 in 196 ms · orders.count 1 → 2
expected 1 · the retry D11 did the same

Each duplicate Stripe sends, and each retry for up to 3 days, creates another order.

FixRecord event.id before creating the order and return 200 early when it is already recorded.
Stripe docs › Webhooks › Handle duplicate events
Medium

Over the 10 s budget for Stripe

D10 11 840 ms (+1 840 over)
D16 10 420 ms (+420 over)
median of the other 6: 202 ms

A slow delivery counts as failed and is retried. Here, the retry after D10 caused the duplicate order.

FixAcknowledge with 200 first, then queue the slow work.

Secrets stay on your machine

The agent signs and sends from your laptop or your CI runner. We see names, never values.

  • Sends deliveries only to targets you allow
  • Keeps signing secrets on your machine (we see names, never values)
  • Probe values stay on your machine. Only small counts and codes reach the server.
  • Open source. Run your own with docker compose up
