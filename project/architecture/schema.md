## 1. Conventions

### 1.1 Identifiers

| Kind | Storage | External form | Example |
| ---- | ------- | ------------- | ------- |
| Entity ids | `uuid` holding a UUIDv7 (time-ordered) | `<prefix>_` + 26-char Crockford base32 of the 128 bits | `run_01M75F1M56RSH0CVKCTFX4FQWC` |
| Prefixes | — | `usr_` `gst_` `wsp_` `prj_` `cap_` `run_` `agt_` `tok_` `job_` `fix_` `rnr_` `key_` (WebAuthn credential) `ses_` (browser sign-in session) | |
| `project_key` | `text`, 10 chars base62, CSPRNG | as is in `/p/{projectKey}` | `Br7nQ2xk9A` |
| `capture_key` | `text`, 12 chars base62, CSPRNG (~71 bits) | as is in `/c/{captureKey}` | `Br7nDLk2Qm9x` |
| Capture number | `integer` per project | `#01` (≥ 2 digits) | |
| Run number | `integer` per project | `Run #3` | |
| Run delivery | `smallint` per run | `D3` | |
| Finding | `smallint` per run | `F2` | |
| Pairing code | stored as HMAC-SHA-256 with a server key | `XXXXX-XXXXX` (10 Crockford base32 symbols without `I L O U`, ≈ 50 bits) | `7KQ2M-XR9TD` |
| Share token | stored as SHA-256 (≥ 128-bit random value) | 22 chars base62 in `/s/{shareToken}` | |
| Token values | stored as SHA-256 | kind prefix + random + checksum (contracts.md §1.1) | `wt_pat_…`, `wt_ci_…`, `wt_rnr_…` |

Route constraints: `run_[0-9A-HJKMNP-TV-Z]{26}`, `captureKey [A-Za-z0-9]{12}`, `projectKey [A-Za-z0-9]{10}`, `D[1-9][0-9]?`, `F[1-9][0-9]?`, capture number `[0-9]{2,6}`.

IDs created by the engine offline (CI runs) are generated by the engine in the same format and must be valid UUIDv7. An upload whose `run_id` already exists: same project and same document hash → `200` with the existing run; otherwise → `409` (first write wins, TM-64).

### 1.2 Types and rules

- Timestamps: `timestamptz` (microsecond precision). Server clock only, via the Clock adapter.
- Hashes: `bytea` (32 bytes for SHA-256). Displayed in hex.
- Enums: `text` + `CHECK (col IN (...))` rather than PostgreSQL enum types (cheaper to evolve).
- JSON: `jsonb` only for derived or display data, never for the raw request (ADR-005).
- Every table: `created_at`, `updated_at` unless immutable (then `created_at` only).
- Foreign keys `ON DELETE CASCADE` along the ownership tree (§8); `RESTRICT` elsewhere.
- **Hosted profile rule (PV, A09):** no column in this schema can hold a raw probe value, probe definition, probe salt, stderr, signing secret, any part of a secret value (no last-4 hint, S-8), signature header value sent by the engine, or agent-authored finding prose. A Pest test lists every column and asserts this set is empty.

### `user_identities`
`id`, `user_id` FK → users CASCADE, `provider` CHECK IN ('github','google'), `provider_subject` text, `provider_email_verified` boolean NOT NULL, `provider_label` text NOT NULL (provider login or email at link time, display only, e.g. `maya-l`; refreshed at each sign-in), `linked_at` timestamptz NOT NULL, `linked_via` text CHECK IN ('signup','oauth_email_match','settings') NOT NULL, UNIQUE (`provider`,`provider_subject`), **UNIQUE (`user_id`,`provider`)** (one GitHub and one Google identity per user; linking a second of the same provider means disconnecting the first). Unlinking deletes the row (domain §2.5). (`email_link` removed: decision 44 lists email + password, not magic links; PO-I, decided in decision 46: no magic link.)

### `totp_factors`
`user_id` uuid PK FK → users CASCADE, `secret` bytea NOT NULL (Laravel encrypter), `confirmed_at` timestamptz (NULL until the first code is accepted), `last_used_step` bigint (a code is accepted once). One per user.

### `recovery_codes`
`id`, `user_id` FK CASCADE, `code_hash` bytea NOT NULL, `used_at` timestamptz. 10 rows per set; regeneration deletes the set. Exists only while `two_factor_enabled_at` is set. Each code carries ≥ 50 bits of entropy (A09 R-K).

### `second_factor_failures` (WA-3, domain §2.1)
`id`, `user_id` FK CASCADE, `failed_at` timestamptz NOT NULL, `kind` CHECK IN ('totp','recovery_code','webauthn'). Index (`user_id`,`failed_at`). One row per failed second-factor attempt, **across** challenges; no code value is stored. The service counts the rows of the last 24 h per user; at 20 it sets `users.second_factor_hold_until`. Rows older than 24 h are deleted hourly.

### `account_recovery_requests` (hosted, domain §2.3)
`id`, `user_id` FK CASCADE, `token_hash` bytea UNIQUE, `requested_at`, `confirmed_at`, `completes_at` (confirmed + 72 h; recomputed to 7 days from the later event when a password reset by email falls in the 7 days before the request or during the wait, RC-2), `wait_extended_at` timestamptz (RC-2), `cancelled_at`, `cancelled_by` text CHECK IN ('user','second_factor_signin','declined','link_expired','email_changed') (RC-1; `declined` = the link holder chose "Cancel, I found my key" on the interstitial before confirming; `link_expired` = not confirmed within 60 min, closed by the hourly job; `email_changed` = an email change closed a not yet confirmed request, its link went to the old address, A09 F12), `completed_at`, `finish_token_hash` bytea UNIQUE and `finish_token_expires_at` timestamptz (the "Set a new password" link sent at completion, 24 h, single use; contracts §3.4), `lock_until` timestamptz (= `completed_at` + 7 days; RC-3: while a request is open or `now() < lock_until`, email change, new personal token with `run` and removal of linked identities are refused; the identity lock covers only `user_identities` rows with `linked_at` earlier than the request's `requested_at`, AR-1). Partial unique index (`user_id`) WHERE `cancelled_at IS NULL AND completed_at IS NULL`. Cool-down (RC-5): a new request is refused for 30 days after `cancelled_at` of the latest row cancelled **after confirmation** (`cancelled_by IN ('user','second_factor_signin')`); a `declined` or `link_expired` row closes the request without a cool-down, so an unconfirmed request started by someone else cannot lock the owner out for 30 days. The confirm link (`token_hash`) works for 60 min after `requested_at`. Audit rows (RC-6) are written to `audit_log` for request, confirmation, extension, cancellation and completion. Completion, in one transaction: remove factors and recovery codes, **clear `password_hash`**, revoke every `user_sessions` row and personal token, cancel any pending `email_change_requests`, set every agent of the user's workspace `needs_reconfirm = true` and clear `agent_targets.approved_at` (RC-4), issue the finish token.

### `email_change_requests` (domain §2.6)
`id`, `user_id` FK CASCADE, `new_email` citext NOT NULL, `token_hash` bytea UNIQUE NOT NULL, `requested_at` timestamptz NOT NULL, `expires_at` timestamptz NOT NULL (= `requested_at` + 60 min; **both** links expire here), `old_required` boolean NOT NULL (revision 6.2, EC-1: true when the account had no second factor at request time; fixed for the life of the request), `old_token_hash` bytea UNIQUE NULL (the old-address link `/email-change-old/{token}`; set only when `old_required`), `new_confirmed_at` timestamptz NULL and `old_confirmed_at` timestamptz NULL (each half's button press; the change applies when `new_confirmed_at` is set and, if `old_required`, `old_confirmed_at` is too), `confirmed_at` (= the change was applied; unchanged meaning), `cancelled_at`, `cancelled_reason` text CHECK IN ('replaced','recovery','user','expired'). Partial unique index (`user_id`) WHERE `confirmed_at IS NULL AND cancelled_at IS NULL` (one pending change; a new request cancels the old one with `replaced`). Either half may be pressed first; the second press applies the change. Confirmation re-checks, in one transaction, that no recovery is open or locked (RC-3) and that `new_email` is still free (`users.email` UNIQUE is the final guard; a conflict gets the uniform "link doesn't work" answer). Rows deleted 30 days after closing.

### `account_deletion_requests` (revision 6.2; domain §2.10, DL-4)
`id`, `user_id` FK CASCADE NOT NULL, `token_hash` bytea UNIQUE NOT NULL (link `/account-deletion/{token}`), `requested_at` timestamptz NOT NULL, `expires_at` timestamptz NOT NULL (= `requested_at` + 1 h), `used_at`, `cancelled_at`, `cancelled_reason` text CHECK IN ('replaced','recovery','user','email_changed','expired'). Partial unique index (`user_id`) WHERE `used_at IS NULL AND cancelled_at IS NULL` (one pending request; a new one cancels the old with `replaced`). Created only for accounts without a second factor, by `DELETE /account`. Using it (the `POST` of the link page) re-checks, in the deletion transaction, RC-3, the last-admin rule and that the account still has no second factor, then runs the tombstone; `used_at` is set in that transaction. Rows are deleted 30 days after closing and with the user at purge (the tombstone closes any pending row; the purge deletes the rest).

### `user_sessions` (domain §2.7)
One row per signed-in browser session of a user, independent of the session driver (Laravel's `sessions` on database or Redis, A10). The row id is stored in the session payload and survives session-id regeneration.

### `password_set_tokens` (revision 6; domain §2.9, §11)

### Atomic quota updates

Guest capture storage, inside the ingest transaction:

```sql
UPDATE guest_sessions SET stored_captures = stored_captures + 1
 WHERE id = $1 AND stored_captures < 100 AND expires_at > now() AND ended_at IS NULL AND claimed_at IS NULL
RETURNING stored_captures;
-- no row → answer identically, store nothing (ADR-005 amendment 1 §4)
```

Guest storage additionally checks the **global guest storage budget** (sum of `guest_sessions.stored_bytes`, kept as one counter row in `instance_counters` updated in the same transaction with a `WHERE total + $size <= budget` guard).

Account projects use the same pattern on `projects` (`captures_today < daily limit` with a day reset, `stored_body_bytes + $size <= byte limit`). Limits come from instance settings (self-host) or configuration (hosted).

Run quota uses the same pattern on `counted_runs < 10`, executed once per run when the engine reports "got past Once", guarded by `runs.quota_counted`. Starting a run checks `counted_runs < 10` and `accepted_runs < 20` without incrementing (a run that fails to start must not burn quota, A-13). `accepted_runs` is incremented at `RunAccepted`.

### `run_jobs`
`id` (`job_`), `run_id` FK CASCADE NULL (NULL for verify jobs), `kind` CHECK IN ('run','verify'), `agent_id` FK → agents CASCADE NULL, `runner_id` FK → runners SET NULL, `capture_ids` uuid[] NOT NULL (the only captures its executor may fetch, TM-35), `expires_at`, `accepted_at`, `completed_at`, `offer_after` timestamptz (AC-8: after a `needs_confirmation`/`needs_reconfirm` decline, not offered to `jobs/next` before this; 30 s), `secrets_fetched_at` timestamptz (self-host B′ only; **RN-6, A09 §12.9**). `CHECK (secrets_fetched_at IS NULL OR runner_id IS NOT NULL)`.

**One secrets fetch per job, atomically (RN-6).** The secrets endpoint first claims the fetch with one conditional update and builds the response only if a row came back:

```sql
UPDATE run_jobs j SET secrets_fetched_at = now()
 WHERE j.id = $job AND j.runner_id = $runner AND j.secrets_fetched_at IS NULL
   AND EXISTS (SELECT 1 FROM runs r WHERE r.id = j.run_id AND r.status = 'running' AND r.executor = 'server_allowlist')
RETURNING j.id;
```

No row → the service looks up why (already fetched → `409` + `RunnerSecretsRefetchBlocked` `second_fetch`; other runner, not accepted, not Running or final → `403` + the matching reason) and writes the audit row. Two concurrent calls cannot both succeed. The claim is not undone if the response then fails to reach the runner: the runner fails the job (`failed: secrets_unavailable`) and the user starts a new run (fail closed). `CHECK (kind = 'verify') <= (agent_id IS NOT NULL)` (verify jobs are issued to one agent only; self-host checks with instance secrets run `verify` in the app and need no job). Verify jobs cascade with their agent; run jobs with their run. Index GIN (`capture_ids`) WHERE `completed_at IS NULL`.

### P2 scrub rules (share views)

Not stored. Applied at render time when a viewer is not a member:

1. **Source capture bodies** (JSON only): every string value matching an SCR-1 value pattern, every pack scrub field path, and every key from the pack's `scrub` list is replaced by `[hidden]`; secret-prefix matches (SCR-1 "block" row) are always replaced; ids matching pack id patterns stay (SCR-2). Non-JSON bodies are hidden entirely.
2. `share_bodies_hidden = true` hides all bodies.
3. **Headers** of source captures: only the SCR-3 allow-list (`Content-Type`, `User-Agent`, pack event-id and topic headers); everything else hidden.
4. **Probe display:** labels and small counts; `opted_*` values only when `share_include_probe_values` (PV-7).
5. Not shown at all: capture URL, capture key, agent secret names, agent target list, target host when it is not loopback (shown as `private host`).
6. Shown: provenance (executor, source, agent name or CI token name, or "Webhook Trap server runner") (TM-17); finding prose from server templates.
7. Share pages: reached only by share token (`/s/{shareToken}`); `Referrer-Policy: no-referrer`; `X-Robots-Tag: noindex`.

The PHP scrubber and the Go scrubber read the same rule data from packs and are tested against one shared corpus (`contracts/scrub/corpus/*.json` with expected outputs).

```
guest_sessions ─┐
users ──────────┴─ workspaces ─┬─ projects ─┬─ capture_urls ── captures ── capture_bodies
                               │            ├─ runs ─┬─ run_scenarios
                               │            │        ├─ run_deliveries

                               │            │        ├─ run_jobs
                               │            │        └─ run_events_inbox
                               │            ├─ fixture_meta
                               │            └─ ci_tokens
                               ├─ agents ─┬─ agent_secret_names
                               │          ├─ agent_targets
                               │          └─ agent_access_tokens

users ─┬─ user_identities
       ├─ webauthn_credentials
       ├─ totp_factors

       ├─ account_recovery_requests
       ├─ email_change_requests
       ├─ user_sessions
       ├─ password_set_tokens
       └─ personal_tokens
```

| Job (queue `maintenance`) | Frequency | Action |
| ------------------------- | --------- | ------ |
| Guest expiry | every minute | `DELETE FROM guest_sessions WHERE expires_at < now() - interval '5 min'` (cascade); access already stopped at `expires_at` |
| Ended/claimed guest sessions | every minute | delete the session (its workspace is gone or moved) |
| Capture retention | daily | delete captures older than the project's retention (bodies cascade) in batches of 5 000 |
| Run retention | daily | delete runs older than the project's run retention (readings cascade, PV-13) |
| Pairing codes, access tokens, claim nonces | hourly | delete expired |
| Unconfirmed agents | every minute | revoke agents unconfirmed 10 min after `pair`, reason `unconfirmed`; `AgentUnconfirmedExpired` (RE-1) |
| Second-factor failures | hourly | delete `second_factor_failures` older than 24 h (WA-3) |
| Account recovery requests | every 5 min | complete confirmed requests past `completes_at`; close unconfirmed ones older than 60 min (`link_expired`); delete closed ones after 30 days |
| Email change requests | hourly | close pending ones past `expires_at` (`expired`, both links); delete closed ones after 30 days |
| Account deletion requests (revision 6.2, DL-4) | hourly | close pending ones past `expires_at` (`expired`); delete closed ones after 30 days |
| User sessions | hourly | mark rows past idle or absolute expiry `revoked_reason = 'expired'`; delete rows revoked or expired more than 30 days ago |
| Account capture counters | daily | reset `captures_today` |
| `run_events_inbox` | hourly | delete for final runs older than 1 h |
| Soft-deleted projects | hourly | hard delete after 24 h |
| Deleted accounts (revision 6) | every 5 min | purge users with `deleted_at` set: workspace tree, then identity tree, then the row, in batches; mask addresses in their `audit_log` rows; must finish ≤ 1 h after `deleted_at` (alert otherwise). **Revision 6.1 (DL-3a):** appends the deletion-ledger entry (idempotent, keyed on `usr_` id) and confirms it is durably written **before** deleting the identity tree and the `users` row; a failed append keeps the row and raises the alert |
| Password-set tokens | hourly | delete used or expired rows older than 30 days |

Backups (A10, TM-81) contain display values and capture bodies: 7-day point-in-time recovery, 14-day encrypted off-server copies, disclosed in the privacy notice (HD-4). **Deleted accounts (revision 6, domain §2.10)** survive only in those backups (≤ 7 days in the PITR window, ≤ 14 days off-server); a deletion ledger kept outside the database (`usr_` id, `deleted_at`) is re-applied after any restore, **before the app, workers and queues start** (revision 6.1, DL-3). The purge job appends the entry and does not delete the `users` row until it is durably written; the off-server copy and retention of the ledger are A10's.
